# SpawnWP 0.5.42

This release prevents running WordPress stacks from collectively reserving more memory than the
host can safely provide. SpawnWP subtracts an operating-system reserve — 20% of physical RAM,
bounded between 512 MiB and 1 GiB — then compares the remaining capacity with the real Docker
cgroup limits of running SpawnWP containers. Stopped sites count as zero.

Creates, explicit **Up** actions and increases to a running site's PHP memory are admitted before
Docker is called. Pending operations reserve their capacity too, closing the race where two valid
requests could arrive together. A refusal is HTTP 409 and reports host RAM, system reserve,
committed, requested and available capacity with the corrective options.

PHP's `memory_limit` is still configurable from 16 MiB through 1 GiB. Its container cap is now
derived automatically as `max(512 MiB, memory_limit + 256 MiB)`, so a 1 GiB PHP limit receives a
1.25 GiB container rather than being killed by the previous fixed 512 MiB cap. The internal
`SPAWNWP_PHP_CONTAINER_MEMORY` value is not a separate Cockpit setting.

The update migrates every existing site's frozen compose file and derives the internal cap from
its current `zz-site.ini`, without restarting or starting any site. A running old container keeps
its actual current cap in the capacity calculation until it is next recreated. PHP settings and
PHP-version changes made while a site is Down are saved, but the site remains Down.

`SPAWNWP_MAX_SITES` remains an independent inventory limit: it counts all saved sites, whether
running or stopped. The new RAM policy controls only which containers may be running together.

The Cockpit now also pins its production-tested Starlette and AnyIO versions. This prevents fresh
dependency resolution from selecting a newer combination that deadlocks the authenticated API
test client.
